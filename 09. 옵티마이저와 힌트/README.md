# 09. 옵티마이저와 힌트

이 장은 MySQL 서버가 동일한 결과를 만들기 위해 어떤 실행 경로를 선택하는지와 그 선택이 성능에 어떤 영향을 주는지를 다룬다.

핵심은 옵티마이저가 어떤 기준으로 실행 계획을 선택하는지 이해하고 정렬, GROUP BY, DISTINCT 같은 연산이 왜 느려질 수 있는지를 파악하는 것이다.

## **9.1 개요**

- SQL은 선언형 언어
- 사용자는 무엇을 원하는지만 작성
- 어떻게 처리할지는 MySQL 옵티마이저가 결정
- 옵티마이저는 여러 실행 방법 중 비용이 가장 낮다고 판단되는 실행 계획을 선택

## **9.1.1 쿼리 실행 절차**

MySQL 쿼리는 크게 세 단계로 처리된다.

1. **SQL 파싱**
    - SQL 문법 검사
    - SQL 파스 트리 생성
2. **최적화**
    - 접근 테이블 결정
    - 인덱스 선택
    - 조인 순서 결정
    - 정렬 및 그룹 처리 방법 결정
3. **실행**
    - 스토리지 엔진으로부터 레코드 읽기
    - 정렬, 조인, 그룹핑 수행
    - 결과 반환

첫 번째와 두 번째 단계는 주로 **MySQL 엔진에서 수행되고,**

세 번째 단계는 **MySQL 엔진과 스토리지 엔진이 함께 수행**한다.

## **9.1.2 옵티마이저의 종류**

### **규칙 기반 옵티마이저(RBO)**

- 사전에 정의된 규칙 기반
- 통계 정보나 데이터 분포를 거의 사용하지 않음
- 항상 동일한 실행 계획을 생성
- 현재는 거의 사용되지 않음

### **비용 기반 옵티마이저(CBO)**

- 테이블 레코드 수
- 인덱스 카디널리티
- 통계 정보
- 예상 I/O 비용

을 기반으로 실행 계획을 선택한다.

MySQL 8.0은 **비용 기반 옵티마이저**를 사용한다.

## **9.2 기본 데이터 처리**

이 절은 **정렬, 스캔, 그룹화** 같은 기본 연산이 어떻게 처리되는지 설명한다.

## **9.2.1 풀 테이블 스캔과 풀 인덱스 스캔**

### **풀 테이블 스캔**

- 테이블을 처음부터 끝까지 모두 읽음
- 옵티마이저가 다음 경우 선택
    - 테이블의 레코드 건수가 너무 적은 경우
    - 적절한 인덱스가 없는 경우
    - 인덱스를 사용해도 이득이 없는 경우

InnoDB에서는 **리드 어헤드(Read Ahead)** 가 동작한다.

- 연속 페이지 읽기 패턴 감지
- 백그라운드 스레드가 미리 페이지를 읽어 버퍼 풀에 적재

### **풀 인덱스 스캔**

- 테이블이 아니라 인덱스를 처음부터 끝까지 스캔
- 테이블 스캔보다 I/O 비용이 적을 수 있음
- 다음 경우 선택
    - 필요한 컬럼이 인덱스에 모두 포함된 경우
    - 테이블보다 인덱스가 훨씬 작은 경우

## **9.2.2 병렬 처리**

MySQL 8.0부터 **하나의 쿼리를 여러 스레드로 병렬 처리할 수 있다.**

- innodb_parallel_read_threads 변수로 제어
- 풀 테이블 스캔 또는 풀 인덱스 스캔에 적용
- WHERE 조건이 없는 COUNT(*) 같은 쿼리에 효과적
- 병렬 처리용 스레드 개수가 CPU 코어 수를 초과하면 오히려 성능이 저하될 수 있다.

## **9.2.3 ORDER BY 처리**

ORDER BY는 항상 정렬 비용을 발생시키지는 않는다.

정렬은 크게 2가지 방식으로 처리된다.

1. 인덱스를 이용한 정렬
2. Filesort를 이용한 정렬

<img width="1020" height="384" alt="image" src="https://github.com/user-attachments/assets/0d4cd809-aec4-4419-9d1b-9811f00fca1f" />

- 인덱스를 이용한 정렬
    - 인덱스 자체가 정렬되어 있으므로 별도 정렬 작업이 없다.
- Filesort
    - 인덱스로 정렬이 불가능할 때 MySQL이 별도의 정렬 단계를 수행한다.
    - 실행 계획 Extra에 Using filesort로 표시된다.

인덱스를 이용한 정렬이 불가능한 상황들

- 정렬 기준이 너무 다양해 모든 인덱스를 만들 수 없다.
- GROUP BY 결과나 DISTINCT 결과를 정렬해야 하는 경우
- UNION 결과처럼 임시 테이블의 결과를 다시 정렬해야 하는 경우
- 랜덤하게 결과 레코드를 가져와야 하는 경우

### **9.2.3.1 소트 버퍼**

- Filesort 수행을 위한 전용 메모리 영역
- 쿼리 실행 중에만 할당되고 종료 시 반환
- 크기는 sort_buffer_size로 제어
- 세션 단위로 할당되므로 동시 정렬 쿼리가 많으면 메모리 사용량이 급증
- 크게 잡는다고 항상 빨라지지 않으며 OOM 위험이 있음

### **9.2.3.2 정렬 알고리즘**

Filesort는 내부적으로 크게 2가지 방식으로 수행된다.

### **싱글 패스 정렬**

- 정렬 키뿐 아니라 SELECT 대상 컬럼까지 함께 소트 버퍼에 담아 정렬
- 장점
    - 정렬 후 테이블을 다시 읽지 않음
- 단점
    - 소트 버퍼에 담는 데이터가 커져 메모리 사용량 증가

<img width="868" height="528" alt="image" src="https://github.com/user-attachments/assets/b7befcdb-6d0c-4ecc-a456-d0caef6c1093" />

- 테이블에서 정렬에 필요한 컬럼과 출력 컬럼을 읽어 소트 버퍼에 적재
- 소트 버퍼에서 정렬
- 정렬된 결과를 바로 반환

### **투 패스 정렬**

- 소트 버퍼에는 정렬 키와 로우 식별자만 저장
- 정렬 후 테이블을 다시 읽어 나머지 컬럼을 가져옴
- 장점
    - 소트 버퍼 사용량이 작음
- 단점
    - 정렬 후 테이블 재접근 비용 발생

<img width="824" height="514" alt="image" src="https://github.com/user-attachments/assets/4b378a88-ac06-4130-a69d-589e2082fcca" />

- 테이블에서 정렬 키와 로우 식별자를 읽어 소트 버퍼에 적재
- 소트 버퍼에서 정렬
- 정렬 결과 순서대로 테이블을 재접근해 나머지 컬럼을 읽음
- 최종 결과 반환

최신 버전에서는 보통 싱글 패스 정렬 방식을 주로 사용하지만, 다음의 경우 투 패스 정렬 방식을 사용한다.

- 레코드 크기가 max_length_for_sort_data 시스템 변수 기준을 넘는 경우
- BLOB, TEXT 타입 컬럼이 SELECT 대상에 포함되는 경우

### **9.2.3.3 정렬 처리 방법**

ORDER BY가 사용되면 MySQL은 실제 실행에서 다음 3가지 중 하나로 처리한다.

위에서 아래로 갈수록 비용이 커진다.

### **9.2.3.3.1 인덱스를 이용한 정렬**

- ORDER BY 컬럼 순서대로 인덱스가 있으면 인덱스를 순서대로 읽기만 하면 됨
- Extra에 Using filesort가 표시되지 않음
- 조인이 있더라도 드라이빙 테이블 순서가 유지되는 경우에만 자연 정렬이 유지됨

```sql
mysql> SELECT *
FROM employees e, salaries s
WHERE s.emp_no = e.emp_no
AND e.emp_no BETWEEN 100002 AND 100020
ORDER BY e.emp_no;
```

### **9.2.3.3.2 조인의 드라이빙 테이블만 정렬**

- 조인 전에 드라이빙 테이블에서 정렬 결과를 만든 뒤 그 순서대로 조인 수행
- 조건
    - ORDER BY 컬럼이 드라이빙 테이블 컬럼만 포함되어야 한다.

```sql
mysql> SELECT *
FROM employees e, salaries s

ORDER BY e.last_name;
```

### **9.2.3.3.3 임시 테이블을 이용한 정렬**

- 조인 결과를 먼저 만든 뒤 임시 테이블에 담고 정렬
- 조인 결과가 커질수록 가장 비싼 방식
- Extra에 Using temporary, Using filesort가 함께 나타나는 경우가 많음

```sql
mysql> SELECT *
FROM employees e, salaries s
WHERE s.emp_no = e.emp_no
AND e.emp_no BETWEEN 100002 AND 100010
ORDER BY s.salary;
```

### **9.2.3.3.4 정렬 처리 방법의 성능 비교**

정렬 성능은 단순 처리 시간뿐 아니라 클라이언트가 언제부터 결과를 받는지도 중요하다.

이를 위해 처리 방식을 다음 2가지로 구분한다.

### **9.2.3.3.4.1 스트리밍 방식**

- 조건에 맞는 레코드를 찾는 즉시 클라이언트로 전송
- 서버가 모든 결과를 모을 필요가 없음
- OLTP에서는 첫 응답이 빨라 체감 성능이 좋음
- LIMIT이 있으면 특히 유리

### **9.2.3.3.4.2 버퍼링 방식**

- 정렬, 그룹핑처럼 결과를 모아야 하는 작업은 버퍼링이 필요
- 서버가 모든 결과를 모은 후 처리하므로 첫 응답이 늦음
- LIMIT이 있어도 후보를 모으는 과정 때문에 이점이 줄어들 수 있음

참고)

- 서버는 스트리밍이어도 클라이언트 드라이버가 내부 버퍼링하면 체감이 달라질 수 있음
예를 들어, JDBC 드라이버는 보통 데이터를 받아서 버퍼에 쌓아두는 방식이 흔하다.

### **9.2.3.4 정렬 관련 상태 변수**

- Sort_merge_passes
    - 멀티 머지 처리 횟수
- Sort_range
    - 인덱스 레인지 스캔 결과 정렬 횟수
- Sort_scan
    - 풀 스캔 결과 정렬 횟수
- Sort_rows
    - 정렬한 전체 레코드 수

정렬 튜닝은 보통 이 값으로 정렬량과 디스크 머지 발생 여부를 판단한다.

## **9.2.4 GROUP BY 처리**

GROUP BY는 인덱스를 쓰는 경우와 그렇지 않은 경우로 나뉜다.

처리방식은 다음 3가지이다.

- 인덱스 스캔
- 루스 인덱스 스캔
- 임시 테이블 사용

### **9.2.4.1 인덱스 스캔을 이용한 GROUP BY**

- GROUP BY 컬럼 순서대로 인덱스가 있으면 인덱스를 순서대로 읽으며 그룹핑

### **9.2.4.2 루스 인덱스 스캔을 이용한 GROUP BY**

- 루스 인덱스 스캔 방식은 인덱스를 건너뛰면서 필요한 부분만 읽어서 가져옴
- MIN, MAX 같은 집계 함수에 유리한 방식

```sql
-- salaries 테이블의 인덱스가 (emp_no, from_date)로 생성되어 있다.
mysql> EXPLAIN
SELECT emp_no
FROM salaries
WHERE from_date = '1985-03-01'
GROUP BY emp_no;
```

### **9.2.4.3 임시 테이블을 사용하는 GROUP BY**

- 인덱스로 처리할 수 없으면 내부 임시 테이블 생성
- 실행 계획의 Extra 컬럼에 Using temporary 표시
- MySQL8.0 버전부터는 GROUP BY로 인해 묵시적인 정렬이 수행되지 않음
    - 내부적으로 GROUP BY 컬럼 조합을 유니크 키로 한 임시 테이블에 누적 계산하는 방식으로 처리

## **9.2.5 DISTINCT 처리**

DISTINCT는 사용 형태에 따라 의미가 달라진다.

### **9.2.5.1 SELECT DISTINCT**

- SELECT 컬럼 조합 전체를 유니크하게 만듦
- 내부적으로 GROUP BY와 유사
- 인덱스로 처리 못하면 임시 테이블이 필요할 수 있음

### **9.2.5.2 집합 함수와 함께 사용된 DISTINCT**

- COUNT(DISTINCT col) 같은 형태
- DISTINCT는 함수 인자 범위에만 적용
- SELECT DISTINCT와 실행 계획과 결과 의미가 달라짐

주의)

- DISTINCT는 함수가 아님
- DISTINCT(col1), col2 형태처럼 사용하면 의도와 다르게 동작할 수 있음

## **9.2.6 내부 임시 테이블 활용**

- MySQL 엔진이 자동으로 만드는 임시 테이블
- 사용자가 만드는 TEMPORARY TABLE과 다름
- 쿼리 종료 시 자동 삭제
- 세션 간 공유 불가

### **9.2.6.1 메모리 임시 테이블과 디스크 임시 테이블**

MySQL 8.0 기준)

- 메모리 임시 테이블은 TempTable 엔진
- 디스크 임시 테이블은 InnoDB 또는 MMAP

전환 기준)

- 임시 테이블 크기
- 컬럼 타입(BLOB, TEXT)
- 관련 시스템 변수

### **9.2.6.2 임시 테이블이 필요한 대표 쿼리**

- ORDER BY + GROUP BY
- DISTINCT + ORDER BY
- UNION, UNION DISTINCT
- 파생 테이블(DERIVED)

### **9.2.6.3 임시 테이블이 디스크에 생성되는 경우**

- 내부 임시 테이블은 기본적으로 메모리에 생성됨
- 메모리에서 처리할 수 없는 경우 디스크로 전환
- 디스크 임시 테이블은 tmpdir에 생성
- 파일은 쿼리 종료 시 삭제됨

### **9.2.6.4 임시 테이블 관련 상태 변수**

- Created_tmp_tables
    - 내부 임시 테이블 생성 횟수 누적값
    - 메모리 디스크 구분 없이 합산
- Created_tmp_disk_tables
    - 디스크에 생성된 내부 임시 테이블만 누적

## **9.3 고급 최적화**

MySQL 옵티마이저는 통계 정보와 옵티마이저 옵션을 함께 고려해 실행 계획을 선택한다.
고급 최적화 기능의 사용 여부는 optimizer_switch로 제어한다.

### **9.3.1 옵티마이저 스위치 옵션**

- optimizer_switch 시스템 변수로 제어
- global, session, 쿼리 힌트, SET_VAR 단위로 설정 가능
- 값은 default, on, off 형태로 제어

### **9.3.1.1 MRR과 배치 키 액세스**

Nested Loop Join의 문제)

- 드라이빙 테이블에서 한 건 읽을 때마다 드리븐 테이블을 즉시 랜덤 접근
- 스토리지 엔진이 최적화할 여지가 작음

### **MRR**

- 조인 키를 먼저 버퍼링
- 정렬된 순서로 한 번에 읽어 랜덤 I/O 감소

### **BKA**

- MRR을 활용한 조인 방식
- 기본적으로 off
- 정렬 비용 때문에 항상 유리하지는 않음

### **9.3.1.2 블록 네스티드 루프 조인(block_nested_loop)**

- join_buffer_size에 의존
- 드라이빙 결과를 조인 버퍼에 모아 두고 드리븐을 처리
- Extra에 Using join buffer 표시
- 조인 결과 순서가 드라이빙 인덱스 순서와 달라질 수 있음
- MySQL 8.0.20 이후 해시 조인으로 대체됨

### **9.3.1.3 인덱스 컨디션 푸시다운(index_condition_pushdown)**

- 인덱스로 범위를 줄일 수 없는 조건이 엔진까지 전달되지 않던 문제를 해결하기 위해 등장
- 인덱스에 포함된 컬럼 조건을 스토리지 엔진 단계에서 함께 평가
- 불필요한 테이블 레코드 읽기 감소
- Extra에 Using index condition 표시
- MySQL 5.6부터 개선됨

### **9.3.1.4 인덱스 확장(use_index_extensions)**

- InnoDB 세컨더리 인덱스 리프 노드에는 프라이머리 키가 포함됨
- 옵티마이저가 이를 활용해 복합 인덱스처럼 사용하는 기능

### **9.3.1.5 인덱스 머지**

- 한 테이블에 대해 여러 인덱스를 동시에 사용하는 실행 계획
- 단일 인덱스로 충분하면 선택되지 않는다.

### **9.3.1.6 교집합(index_merge_intersection)**

- AND 조건
- 여러 인덱스 결과의 교집합
- Extra에 Using intersect 표시

### **9.3.1.7 합집합(index_merge_union)**

- OR 조건
- 여러 인덱스 결과의 합집합
- 중복 제거 필요

### **9.3.1.8 정렬 후 합집합(index_merge_sort_union)**

- 합집합 시 정렬이 필요한 경우
- Extra에 Using sort_union 표시

### **9.3.1.9 세미 조인(semi join)**

서브쿼리의 존재 여부만 판단하는 조인

세미 조인 최적화 전략)

- FirstMatch
- LooseScan
- Materialization
- Duplicate Weedout
- Table Pullout

### **9.3.1.10 테이블 풀 아웃**

- IN 서브쿼리를 JOIN 형태로 재작성하는 최적화
- 실행 계획에 별도 표시 없음
- SHOW WARNINGS로 재작성 확인
- 조건이 맞으면 성능상 유리

### **9.3.1.11 FirstMatch**

- EXISTS 형태의 세미 조인
- 첫 매칭 레코드 발견 시 즉시 중단
- Extra에 FirstMatch 표시
- 특정 형태의 서브쿼리에 제한 존재

### **9.3.1.12 루스 스캔**

- 루스 인덱스 스캔을 이용한 세미 조인 최적화
- Extra에 LooseScan 표시

### **9.3.1.13 Materialization**

- 서브쿼리 결과를 임시 테이블로 만든 뒤 조인
- 실행 계획에 MATERIALIZED 표시
- 임시 테이블 생성 비용이 발생하지만 유리한 경우가 있음

### **9.3.1.14** Duplicate Weedout

- 중복 제거를 위해 임시 테이블 사용
- Start temporary, End temporary 구간으로 표시되는 형태가 있음

### **9.3.1.15 컨디션 팬아웃 필터**

- 조건별 필터링 비율 추정의 정확도를 개선
- filtered 값 변화로 확인 가능
- 통계 정보 히스토그램 인덱스 정보를 활용

### **9.3.1.16 파생 테이블 머지**

- FROM 절 서브쿼리를 외부 쿼리로 병합하는 최적화
- derived_merge로 제어
- 집계, DISTINCT, LIMIT, UNION 등이 있으면 제한될 수 있음

### **9.3.1.17 인비저블 인덱스**

- 인덱스를 삭제하지 않고 옵티마이저 선택 대상에서만 제외
- 인덱스 영향도 검증에 유용
- use_invisible_indexes 옵션이 필요할 수 있음

### **9.3.1.18 스킵 스캔**

- 선행 컬럼 조건이 없어도 후행 컬럼 조건으로 인덱스를 활용
- 선행 컬럼의 유니크 값 종류가 적을 때 효과적
- 힌트로 강제 가능

### **9.3.1.19 해시 조인**

- MySQL 8.0.18부터 도입
- 빌드 단계와 프로브 단계로 수행
- join buffer 사용
- Nested Loop Join이 부적합한 경우 대체 전략 성격
- 메모리 초과 시 Grace hash join 방식으로 디스크를 사용

### **9.3.1.20 인덱스 정렬 선호**

- ORDER BY, GROUP BY를 인덱스로 처리하려는 경향이 실행 계획 선택에 영향을 줌
- prefer_ordering_index 옵션으로 제어 가능
- 잘못된 선택을 보정하기 위한 목적

## **9.3.2 조인 최적화 알고리즘**

- 조인 테이블 수가 많아질수록 실행 계획 탐색 비용 급증
- MySQL은 실행 계획 수립 자체가 병목이 될 수 있음

### **9.3.2.1 Exhaustive 검색 알고리즘**

- 모든 테이블 조합을 평가해 최적 조합을 선택
- 테이블 수가 늘면 팩토리얼 수준으로 경우의 수 폭증
- 테이블 10개만 넘어도 실행 계획 수립에 수 분 소요 가능
- 현재는 거의 사용되지 않음

### **9.3.2.2 Greedy 검색 알고리즘**

- Exhaustive의 시간 폭증을 줄이기 위해 도입
- 부분 실행 계획을 점진적으로 확장
- optimizer_search_depth로 탐색 깊이 제한

## **9.4 쿼리 힌트**

- 옵티마이저가 항상 최적의 실행 계획을 선택하지는 않음
- 개발자가 실행 계획에 개입할 수 있는 수단이 쿼리 힌트
- 힌트는 최후의 수단으로 사용하는 것이 원칙

### **9.4.1 인덱스 힌트**

- USE INDEX
- FORCE INDEX
- IGNORE INDEX
- ANSI SQL 비표준
- SELECT UPDATE에서만 사용 가능
- 가능하면 옵티마이저 힌트 사용 권장

### **9.4.1.1 STRAIGHT_JOIN**

- 조인 순서를 FROM 절에 작성한 순서로 고정
- 드라이빙 테이블 선택에 개입 가능
- 잘못 사용 시 성능 악화 가능

### **9.4.1.3 SQL_CALC_FOUND_ROWS**

- LIMIT 적용 쿼리에서 전체 레코드 수 계산 목적
- 내부적으로 전체 검색 수행
- 성능 비용 매우 큼
- 대부분의 경우 SQL_CALC_FOUND_ROWS 사용 비권장
- COUNT 쿼리와 데이터 조회 쿼리 분리 권장

### **9.4.2 옵티마이저 힌트**

분류 기준)

- 인덱스 수준
- 테이블 수준
- 쿼리 블록 수준
- 전역 수준

### **9.4.2.2 MAX_EXECUTION_TIME**

- 쿼리 최대 실행 시간 제한
- 실행 계획에는 영향 없음
- 타임아웃 제어 목적

### **9.4.2.3 SET_VAR**

- 쿼리 단위로 시스템 변수 조정
- optimizer_switch, join_buffer_size 등 제어 가능
- 모든 변수를 제어할 수 있는 것은 아님

### **9.4.2.4 SEMIJOIN & NO_SEMIJOIN**

- 세미 조인 최적화 전략 선택을 제어
- Duplicate, Weedout, FirstMatch, LooseScan, Materialization
- Table Pullout은 힌트로 제어 불가

### **9.4.2.5 SUBQUERY**

- 서브쿼리 최적화 방식 제어
- IN to EXISTS
- Materialization
- 안티 세미 조인에는 적용 불가

### **9.4.2.6 BNL & NO_BNL & HASHJOIN & NO_HASHJOIN**

- MySQL 8.0.20 이후 BNL은 해시 조인 유도 용도로 의미가 변경됨
- HASHJOIN 힌트는 8.0.18 전용
- 최신 버전에서는 BNL 계열로 해시 조인을 제어

### **9.4.2.7 JOIN_FIXED_ORDER & JOIN_ORDER & JOIN_PREFIX & JOIN_SUFFIX**

- STRAIGHT_JOIN 단점 보완
- 일부 테이블만 조인 순서를 고정할 수 있음

### **9.4.2.8 MERGE & NO_MERGE**

- 서브쿼리를 외부 쿼리로 병합할지 여부를 제어
- 불필요한 임시 테이블 생성을 줄이는 목적

### **9.4.2.9 INDEX_MERGE & NO_INDEX_MERGE**

- 인덱스 머지 사용 여부를 제어
- 항상 빠른 것이 아니므로 상황에 따라 판단

### **9.4.2.10 NO_ICP**

- 인덱스 컨디션 푸시다운 비활성화
- 옵티마이저 오판 방지 목적

### **9.4.2.11 SKIP_SCAN & NO_SKIP_SCAN**

- 선행 컬럼 조건 없이 인덱스 사용
- 유니크 값 많을 경우 비효율적

### **9.4.2.12 INDEX & NO_INDEX**

- 기존 인덱스 힌트를 옵티마이저 힌트로 대체
- GROUP_INDEX, ORDER_INDEX 등 포함

## **9장 전체 정리**

- 옵티마이저는 비용 기반으로 실행 계획을 선택하며 이 선택은 결과가 같더라도 성능을 크게 바꾼다.
- 성능 문제의 큰 축은 다음이다.
    - 불필요한 전체 스캔이 발생하는가
    - 정렬과 그룹핑이 인덱스로 해결되는가
    - 임시 테이블이 생성되는가
    - 조인 방식과 조인 순서가 적절한가
- ORDER BY, GROUP BY, DISTINCT는 결과를 모아서 처리해야 하는 경우가 많아 버퍼링 방식이 되기 쉽고, 임시 테이블과 filesort로 이어지면 비용이 급증한다.
- 내부 임시 테이블은 자동으로 만들어지며 메모리에서 처리하지 못하면 디스크로 전환되어 비용이 커질 수 있다. 상태 변수를 통해 임시 테이블 생성과 디스크 전환 여부를 확인할 수 있다.
- 고급 최적화 기능은 optimizer_switch로 제어되며, MRR, BKA, ICP, 인덱스 머지, 세미 조인, 파생 테이블 머지, 스킵 스캔, 해시 조인 같은 기능이 포함된다.
    
    이들은 특정 조건에서 큰 이득을 주지만 항상 유리하지는 않다.
    
- 조인 테이블 수가 많아지면 실행 자체보다 실행 계획 수립 비용이 병목이 될 수 있으며 이를 위해 Greedy 기반 탐색과 가지치기 옵션들이 제공된다.
- 힌트는 옵티마이저가 잘못된 선택을 할 때 보정하는 수단이며, 남용하면 버전 변화나 데이터 분포 변화에 취약해져 유지보수 비용이 커진다.
    
    따라서 튜닝의 우선순위는 쿼리와 인덱스 설계를 개선하고, 통계 정보를 신뢰할 수 있게 유지하며, 마지막 수단으로 힌트를 사용하는 흐름이 되어야 한다.
