# 10. 실행 계획

## **10.1 통계 정보**

- MySQL 옵티마이저는 비용 기반 최적화를 수행하며 이를 위해 통계 정보를 사용한다.
- 통계 정보가 부정확하면 옵티마이저는 실제 데이터 특성과 맞지 않는 실행 계획을 선택할 수 있다.
- 실행 계획은 EXPLAIN 명령으로 확인할 수 있지만, 이를 제대로 해석하려면 MySQL 내부 처리 방식과 통계 정보가 어떤 의미를 가지는지 이해해야 한다.
- MySQL 8.0에서는 실행 계획의 정확도를 높이기 위해 통계 정보 관리 방식이 개선되었고, 컬럼 단위 데이터 분포를 저장하는 히스토그램 기능이 도입되었다.

### **10.1.1 테이블 및 인덱스 통계 정보**

- 비용 기반 최적화에서 가장 중요한 요소는 통계 정보다.
- 통계 정보가 정확하지 않으면 옵티마이저는 실제와 전혀 다른 실행 계획을 선택할 수 있다.
- MySQL 5.7 이전에는 테이블과 인덱스에 대해 제한적인 통계 정보만 사용했으며 데이터 분포를 알 수 없었다.
- MySQL 8.0부터는 인덱스와 컬럼의 **데이터 분포를 저장하는 히스토그램** 기능이 도입되었다.

### **MySQL 서버의 통계 정보 관리 방식**

MySQL 5.6 이전까지 InnoDB 통계 정보는 메모리에만 저장되었으며 서버 재시작 시 모두 초기화되었다.

MySQL 5.6부터는 InnoDB 통계 정보가 영구적으로 관리되도록 개선되었으며 다음 테이블에 저장된다.

- mysql.innodb_index_stats
- mysql.innodb_table_stats

이로 인해 서버 재시작 후에도 통계 정보가 유지된다.

### **통계 정보 컬럼 의미**

innodb_index_stats 주요 항목

- n_diff_pfx: 인덱스가 가진 유니크 값의 개수
- n_leaf_pages: 인덱스 리프 노드 페이지 수
- size: 인덱스 전체 페이지 수

innodb_table_stats 주요 항목

- n_rows: 테이블 전체 레코드 수
- clustered_index_size: 프라이머리 키 인덱스 크기
- sum_of_other_index_sizes: 프라이머리 키를 제외한 인덱스 크기 합

### **통계 정보 갱신**

다음 경우 통계 정보가 자동으로 갱신될 수 있다.

- 테이블 오픈
- 대량 INSERT, UPDATE, DELETE 발생
- ANALYZE TABLE 실행
- SHOW TABLE STATUS 또는 SHOW INDEX 실행
- InnoDB 모니터 활성화

통계 정보 자동 갱신은 innodb_stats_auto_recalc 시스템 변수로 제어할 수 있다.

### **10.1.2 히스토그램**

- 기존 통계 정보는 유니크 값 개수만 제공하므로 데이터 분포의 불균형을 반영하지 못했다.
- MySQL 8.0부터는 컬럼 단위 데이터 분포를 저장하는 히스토그램 기능이 도입되었다.
- 히스토그램은 자동 수집되지 않으며 ANALYZE TABLE … UPDATE HISTOGRAM 명령으로 수동 생성한다.
- 히스토그램 정보는 information_schema.column_statistics 테이블에 저장된다.

### **히스토그램과 인덱스 관계**

- 인덱스가 존재하는 컬럼의 경우, 옵티마이저는 히스토그램보다 인덱스 다이브를 우선적으로 사용한다.
- 인덱스 다이브는 실제 인덱스 B-Tree를 샘플링해 조건에 일치하는 레코드 수를 추정하는 방식이다.
- 히스토그램은 주로 인덱스가 없는 컬럼의 선택도 추정에 사용된다.

### **10.1.3 코스트 모델**

- MySQL 서버는 쿼리 실행 시 필요한 작업을 여러 단위 작업으로 분해하고 각 작업 비용을 합산하여 실행 계획을 선택한다.
- 이때 사용하는 비용 기준을 코스트 모델이라 한다.

### **비용 관리 테이블**

MySQL 8.0에서는 코스트 모델 설정값이 다음 테이블에 저장된다.

- server_cost: 인덱스 비교 비용, 레코드 평가 비용, 임시 테이블 처리 비용 등을 포함한다.
- engine_cost: 데이터 페이지 읽기 비용을 포함한다.

### **주요 비용 항목 의미**

engine_cost 테이블 주요 항목은 다음과 같다.

- io_block_read_cost
- memory_block_read_cost
- disk_temptable_create_cost
- disk_temptable_row_cost

server_cost 테이블 주요 항목은 다음과 같다.

- key_compare_cost
- memory_temptable_create_cost
- memory_temptable_row_cost
- row_evaluate_cost

### **코스트 모델 설정 주의사항**

- 코스트 모델 값은 MySQL 서버 내부 동작과 밀접하게 연결되어 있다.
- 기본값은 오랜 기간 실전에서 검증된 값이므로 명확한 목적 없이 변경하지 않는 것이 바람직하다.

## **10.2 실행 계획 확인**

MySQL 서버의 실행 계획은 DESC 또는 EXPLAIN 명령으로 확인할 수 있다.

MySQL 8.0부터는 EXPLAIN 명령에 다양한 FORMAT 옵션이 추가되었다.

### **10.2.1 실행 계획 출력 포맷**

MySQL 8.0에서는 다음과 같은 실행 계획 출력 포맷을 제공한다.

- 기본 테이블 포맷
- TREE 포맷
- JSON 포맷

FORMAT 옵션은 출력 형태만 바꾸며, 실행 계획의 본질은 동일하다.

### **10.2.2 쿼리의 실행 시간 확인**

MySQL 8.0.18부터 EXPLAIN ANALYZE 기능이 추가되었다.

EXPLAIN ANALYZE는 실제 쿼리를 실행한 뒤 다음 정보를 출력한다.

- 단계별 실제 실행 시간
- 처리된 레코드 수
- 반복 횟수

실행 시간이 오래 걸리는 쿼리를 분석할 때 유용하지만, 먼저 EXPLAIN으로 실행 계획을 검토한 후 사용하는 것이 권장된다.

## **10.3 실행 계획 분석**

실행 계획 분석에서 중요한 것은 출력 포맷이 아니라 각 컬럼이 의미하는 바를 이해하는 것이다.

이 절에서는 기본 테이블 포맷 기준으로 실행 계획 컬럼을 설명한다.

### **10.3.1 id 컬럼**

- id 컬럼은 단위 SELECT 쿼리의 식별자다.
- 실행 순서를 의미하지 않는다.
- 조인된 테이블은 동일 id 값을 가질 수 있다.
- 서브쿼리가 포함되면 id 값이 증가한다.
- 실제 실행 순서는 TREE 포맷을 통해 확인해야 한다.

### **10.3.2 select_type 컬럼**

- select_type은 단위 SELECT 쿼리의 유형을 나타낸다.

### **SIMPLE**

- UNION이나 서브쿼리를 사용하지 않은 단순 SELECT
- 조인이 포함되어 있어도 SIMPLE로 표시

### **PRIMARY**

- UNION이나 서브쿼리를 포함한 쿼리에서 가장 바깥에 있는 SELECT

### **UNION**

- UNION으로 결합된 두 번째 이후 SELECT

### **DEPENDENT UNION**

- UNION으로 결합된 단위 SELECT 중에서 **외부 SELECT 쿼리의 컬럼 값에 의존하는 경우** 표시
- 외부 쿼리 결과에 따라 반복 실행된다.

### **UNION RESULT**

- UNION 결과를 저장하는 임시 테이블
- 실제 SELECT 쿼리는 아니며 id 값이 없다.
- MySQL 8.0 버전부터 UNION만 임시 테이블이 필요하고, UNION ALL은 임시 테이블이 필요 없다.

### **SUBQUERY**

- FROM 절 이외에서 사용된 서브쿼리

### **DEPENDENT SUBQUERY**

- 외부 SELECT의 컬럼 값을 참조하는 서브쿼리
- 외부 쿼리 결과에 따라 반복 실행된다.

### **DERIVED**

- FROM 절에 사용된 서브쿼리
- DERIVED는 단위 SELECT 쿼리의 실행 결과로 메모리나 디스크에 임시 테이블(파생 테이블)을 생성하는 것을 의미한다.

### **DEPENDENT DERIVED**

- 외부 컬럼을 참조하는 FROM 절 서브쿼리
- MySQL 8.0부터 LATERAL JOIN으로 지원된다.

### **UNCACHEABLE SUBQUERY**

- 캐시가 불가능한 서브쿼리
- 대표적인 원인
    - 사용자 변수 사용
    - 비결정적 함수 사용
    - RAND(), UUID() 등

### **MATERIALIZED**

- IN 서브쿼리 최적화를 위해 서브쿼리 결과를 임시 테이블로 구체화하여 처리

### **10.3.3 table 칼럼**

- 실행 계획은 단위 SELECT 기준이 아니라 **테이블 기준**으로 표시된다.
- table 칼럼은 각 실행 단계에서 접근하는 테이블 이름이 표시된다.
- \<derived N\> 형태는 서브쿼리 결과로 만들어진 **파생 테이블**을 의미한다.
    - N은 단위 SELECT의 id 값이며 \<derived2\>라면 id=2의 결과로 만든 임시 테이블을 뜻한다.
- MATERIALIZED가 포함된 실행 계획에서도 table 칼럼은 <subquery N> 같은 형태로 표시될 수 있으며, 이는 **서브쿼리 결과를 구체화해서 임시 테이블로 만들었다**는 의미로 이해하면 된다.

## **10.3.4 partitions 칼럼**

- 파티션 테이블을 대상으로 실행 계획을 확인할 때, **실제로 접근한 파티션 목록**이 partitions 칼럼에 표시된다.
- WHERE 조건을 기반으로 읽을 필요가 있는 파티션만 선택하는데, 이 과정을 **파티션 프루닝(Partition pruning)** 이라고 한다.
- 실행 계획에 표시된 파티션만 읽으며, 나머지 파티션은 접근하지 않는다.

## **10.3.5 type 칼럼**

- type 칼럼은 MySQL이 각 테이블을 읽을 때 사용하는 **접근 방식(Access type)** 을 의미한다.
- 매뉴얼에서는 조인 타입이라고 부르기도 하지만, 실제 해석은 조인보다 **인덱스를 어떤 방식으로 썼는지, 또는 테이블을 어떻게 훑는지**에 초점을 둔다.
- 일반적으로 위에 나열될수록 빠른 접근 방식이며, 옵티마이저는 비용을 계산해 선택한다.

### **system**

- 레코드가 1건이거나 매우 작아서, 사실상 상수처럼 취급 가능한 테이블 접근
- InnoDB에서는 거의 보기 어렵고, MyISAM이나 MEMORY 같은 엔진에서 주로 나타난다.
- 실행 계획에서 system이면 해당 단계는 사실상 비용이 거의 없다.

### **const**

- 프라이머리 키 또는 유니크 인덱스의 **모든 칼럼을 등호 조건**으로 비교해 결과가 1건임이 보장되는 접근
- 다른 DBMS에서는 유니크 인덱스 스캔으로 부르는 경우가 많다.
- 복합 프라이머리 키나 복합 유니크 인덱스에서 일부 칼럼만 조건으로 쓰면 const가 아니라 ref로 내려갈 수 있다.
- 옵티마이저가 이 테이블을 먼저 읽어 상수처럼 취급하는 최적화를 수행할 수도 있다.

### **eq_ref**

- 조인에서 자주 나오는 타입
- 조인된 테이블을 읽을 때, 프라이머리 키 또는 유니크 인덱스를 사용해서 **매 조인 키마다 정확히 1건**이 매칭되는 접근
- 특징은 “조인 후행 테이블에서 1건 보장”이다.
- 유니크 인덱스가 NOT NULL이어야 1건 보장이 명확해지는 경우가 많다.

### **ref**

- eq_ref처럼 등호 조건 기반이지만, 1건이 보장되지 않는 접근
- 프라이머리 키나 유니크 인덱스를 전부 사용하지 않아도 되고, 일반 인덱스도 가능하다.
- 반환 레코드가 여러 건일 수 있으므로 const나 eq_ref보다는 보통 느리다.
- 그래도 등호 검색이라 대체로 빠른 편이며 실무에서 가장 흔히 보는 타입 중 하나다.

### **fulltext**

- 전문 검색 인덱스를 사용한 접근
- MATCH … AGAINST 구문을 통해 수행되며, 일반 B-Tree 인덱스 접근과는 성격이 다르다.
- 전문 검색 조건이 포함되면 다른 조건보다 우선적으로 fulltext 접근이 선택되는 경우가 있다.
- 전용 인덱스와 전용 문법이 필요하고, 통계 기반 비용 계산 방식도 일반 인덱스와 다르게 동작할 수 있다.

### **ref_or_null**

- ref 접근에 NULL 비교가 추가된 형태
- 등호 조건 검색과 함께 컬럼 IS NULL 조건이 동시에 포함된 경우에 사용된다.
- 접근 방식의 특성상 ref와 동일하게 인덱스를 사용하지만, NULL 값에 대한 비교가 추가로 수행된다.
- 실무에서 자주 사용되는 접근 방식은 아니지만, 실행 계획에서 이 값이 표시된다면 인덱스 기반 검색에 NULL 조건이 포함되어 있음을 의미한다.

### **unique_subquery**

- IN (subquery) 형태의 조건에서 서브쿼리의 결과가 중복되지 않는다고 옵티마이저가 판단한 경우 사용하는 접근 방식이다.
- 서브쿼리 결과가 유니크하다는 전제하에, 별도의 중복 제거 작업 없이 바로 비교가 가능하다.
- 주로 서브쿼리 내부에서 프라이머리 키나 유니크 인덱스를 기준으로 결과가 생성되는 경우에 선택된다.

### **index_subquery**

- IN (subquery) 형태의 조건에서 서브쿼리 결과에 중복 가능성이 있으나, 인덱스를 이용해 이를 효율적으로 처리할 수 있을 때 사용하는 접근 방식이다.
- 서브쿼리 결과 집합에 대해 인덱스를 사용해 중복 제거 또는 비교 작업을 수행한다.
- unique_subquery와 달리 결과의 유니크성이 보장되지 않지만, 인덱스를 활용해 성능 저하를 최소화하는 것이 목적이다.

### **range**

- 인덱스를 사용하되, 등호가 아니라 범위 조건으로 읽는 접근
- BETWEEN, 부등호, LIKE의 일부 패턴, IS NULL 같은 조건에서 range가 나올 수 있다.
- range는 인덱스를 쓰지만, 읽는 범위가 커지면 비용이 급격히 커질 수 있다.

### **index_merge**

- 하나의 테이블에서 2개 이상 인덱스를 동시에 사용해 결과를 합치는 접근
- 여러 인덱스를 읽고, 결과를 합치거나 교집합을 만드는 추가 작업이 들어간다.
- 실행 계획에서 key가 여러 개로 표시되고 Extra에 union이나 intersect 같은 표현이 같이 나온다.

### **index**

- 테이블 전체를 읽는데, 데이터 레코드가 아니라 **인덱스 전체를 처음부터 끝까지 스캔**하는 접근
- 풀 테이블 스캔(ALL)과 비슷해 보이지만, 인덱스만 읽어서 처리할 수 있는 경우 I/O가 줄어 더 유리할 수 있다.
- 단, 결국 조건으로 작업 범위를 줄이지 못하면 느릴 수 있다.

### **ALL**

- 인덱스를 사용하지 못하고 테이블을 처음부터 끝까지 읽는 풀 테이블 스캔
- 보통 가장 비용이 큰 방식으로 취급된다.
- 다만 조건이 매우 비선택적이거나, 인덱스를 써도 거의 전부 읽어야 하는 상황에서는 옵티마이저가 ALL을 선택할 수 있다.
- DW나 배치처럼 대량 처리에서는 오히려 잘못된 인덱스 튜닝보다 ALL이 나은 경우도 있다는 점이 포인트다.

### **10.3.6 possible_keys 칼럼**

- possible_keys는 **사용 가능한 인덱스 후보 목록**이다.
- 중요한 점은 실제로 사용한 인덱스가 아니라, 옵티마이저가 실행 계획을 만들며 고려한 후보라는 것이다.
- possible_keys에 인덱스가 많이 나열되어도 실제로는 사용되지 않을 수 있다.
- possible_keys가 비어 있거나 NULL이면, 그 단계에서 인덱스를 통한 접근이 후보로 올라오지 않았다는 의미다.

## **10.3.7 key 칼럼**

- key 칼럼은 **최종적으로 선택되어 사용된 인덱스**를 의미한다.
- key가 PRIMARY라면 프라이머리 키 인덱스를 사용한다.
- 일반적으로 index_merge가 아니라면 한 단계에서 하나의 인덱스만 사용한다.
- index_merge가 사용되면 key 칼럼에 여러 인덱스가 쉼표로 함께 표시될 수 있다.
- type이 ALL처럼 인덱스를 사용하지 못한 경우 key는 NULL로 표시된다.

## **10.3.8 key_len 칼럼**

- key_len은 인덱스를 사용할 때 **실제로 비교에 사용된 키 길이(바이트)** 를 의미한다.
- 복합 인덱스라면 몇 개 칼럼까지 사용했는지 추정하는 데 도움된다.
- 복합 프라이머리 키나 복합 인덱스에서 일부 칼럼만 조건으로 사용하면 key_len도 그 일부 길이만큼만 표시된다.
- NULL 허용 칼럼이 인덱스에 포함되면, NULL 여부를 저장하기 위한 추가 1 바이트가 key_len에 포함될 수 있어 타입 길이보다 약간 더 크게 보일 수 있다.

### **10.3.9 ref 칼럼**

- ref 칼럼은 인덱스 탐색 시 **어떤 값으로 인덱스를 찾았는지**를 보여준다.
- 상수를 비교에 사용하면 const로 표시된다.
- 다른 테이블의 칼럼 값을 참조해 조인 조건으로 인덱스를 타면 db.table.column 형태로 표시된다.
- func로 표시되는 경우가 있는데, 이는 참조값이 단순 칼럼 값이 아니라 **변환이나 연산이 개입된 값**이라는 의미다
    - 예를 들어 조인 칼럼 타입이 맞지 않아 내부 변환이 발생하거나, 산술 표현식이 들어간 경우에 나타날 수 있다.
    - 가능하면 조인 칼럼 타입을 맞춰 func가 나오지 않게 만드는 것이 일반적으로 유리하다.

### **10.3.10 rows 칼럼**

- rows는 옵티마이저가 해당 단계에서 **읽어야 한다고 예측한 레코드 건수**다.
- 실제 반환 레코드 수가 아니라, 실행 비용 계산을 위한 추정치다.
- 통계 정보에 기반한 예측이므로 정확하지 않을 수 있다.
- 실행 계획에서 rows가 큰 단계가 병목이 될 가능성이 크다.
- 어떤 경우에는 인덱스가 존재해도 rows 관점에서 더 많은 비교가 필요하다고 판단되어 ALL을 선택하는 경우가 있다.

### **10.3.11 filtered 칼럼**

- filtered는 rows로 읽어온 레코드 중 **추가 조건을 적용한 뒤 최종적으로 남을 것으로 예상되는 비율**을 의미한다.
- 즉, rows가 읽기량이라면 filtered는 그중에서 **통과 비율**이다.
- WHERE 조건 중 인덱스로 처리되지 못하는 조건까지 고려해 최종 남는 비율을 추정한다.
- 조인에서 driving 테이블 선택에도 영향을 줄 수 있다.
    - 같은 인덱스를 쓰더라도 filtered가 낮아 최종 결과가 적을 것으로 예상되는 쪽이 선행 테이블이 될 가능성이 있다.
- MySQL 8.0은 filtered 추정을 더 정확히 하기 위해 히스토그램 같은 기능을 도입했다는 흐름으로 이해하면 된다.

## **10.3.12 Extra 칼럼**

- Extra 칼럼은 실행 계획에서 성능과 관련된 부가 정보를 문자열 형태로 표시한다.
- 보통 여러 개의 문구가 동시에 출력될 수 있으며 각 문구의 순서는 성능 우선순위와 무관하다.
- MySQL 버전이 올라가거나 새로운 최적화가 도입되면 Extra 칼럼에 새로운 메시지가 추가될 수 있다.

### **const row not found**

- const 접근 방식으로 테이블을 읽었지만 실제로 일치하는 레코드가 하나도 없을 때 표시된다.
- 주로 테스트 데이터가 부족하거나 조건이 잘못된 경우이며 실제 성능 문제와는 직접적인 관련은 없다.

### **Deleting all rows**

- 스토리지 엔진이 테이블의 모든 레코드를 한 번의 핸들러 호출로 삭제할 수 있을 때 표시된다.
- WHERE 조건이 없는 DELETE 문에서 주로 나타난다.
- MySQL 8.0에서는 InnoDB와 MyISAM 모두 이 메시지를 더 이상 표시하지 않으며 전체 삭제는 TRUNCATE TABLE 사용이 권장된다.

### **Distinct**

- DISTINCT 처리를 위해 불필요한 조인을 제거하고 필요한 레코드만 읽었음을 의미한다.
- 실행 계획에서 Distinct가 표시되면 중복 제거를 효율적으로 수행하고 있음을 나타낸다.

### **FirstMatch**

- 세미 조인 최적화 전략 중 하나로 조인 대상 테이블에서 첫 번째로 일치하는 레코드를 찾으면 더 이상 탐색하지 않는다.
- 주로 IN 서브쿼리나 EXISTS 형태에서 사용된다.

### **Full scan on NULL key**

- IN 또는 NOT IN 서브쿼리에서 비교 대상 값이 NULL일 수 있어 서브쿼리를 풀 스캔해야 할 때 표시된다.
- 비교 컬럼이 NOT NULL임을 명시하면 이 메시지를 피할 수 있다.

### **Impossible HAVING**

- HAVING 절의 조건을 만족하는 레코드가 논리적으로 존재할 수 없을 때 표시된다.
- 쿼리 자체는 문법적으로 정상이나 결과는 항상 빈 집합이 된다.

### **Impossible WHERE**

- WHERE 조건이 항상 FALSE가 되는 경우 표시된다.
- Impossible HAVING과 동일하게 실행 계획을 만들기 위한 의미 있는 입력 데이터가 없음을 나타낸다.

### **LooseScan**

- 세미 조인 최적화 전략 중 하나로 인덱스를 듬성듬성 스캔해 필요한 키 값만 읽는다.
- IN 서브쿼리 처리 시 자주 사용된다.

### **No matching min max row**

- MIN 또는 MAX 함수가 사용된 쿼리에서 조건을 만족하는 레코드가 하나도 없을 때 표시된다.
- 결과는 NULL이 반환된다.

### **no matching row in const table**

- 조인 대상 테이블을 const 방식으로 접근했지만 일치하는 레코드가 없을 때 표시된다.

### **No matching rows after partition pruning**

- 파티션 프루닝 결과 대상 파티션 자체가 없을 때 표시된다.
- 실제로 삭제되거나 조회될 레코드가 없음을 의미한다.

### **No tables used**

- FROM 절이 없는 쿼리 또는 FROM DUAL 형태의 쿼리에서 표시된다.
- 실제 테이블 접근 없이 메타 정보만 반환한다.

### **Not exists**

- 안티 조인을 수행할 때 사용된다.
- LEFT JOIN 후 NULL 조건으로 필터링하거나 NOT EXISTS 형태의 쿼리에서 표시된다.
- 조인 대상 테이블에 일치하는 레코드 존재 여부만 확인한다.

### **Plan isn’t ready yet**

- EXPLAIN FOR CONNECTION을 사용했을 때 다른 커넥션의 실행 계획이 아직 준비되지 않은 경우 표시된다.

### **Range checked for each record**

- 조인 조건이 두 컬럼 간 비교로 구성되어 있어 레코드마다 인덱스 범위를 다시 계산해야 할 때 표시된다.
- 인덱스가 있어도 효율적인 조인 순서를 결정하기 어려운 경우 발생한다.

### **Recursive**

- WITH RECURSIVE 구문을 사용한 재귀 CTE 실행 계획에서 표시된다.

### **Rematerialize**

- 래터럴 조인에서 외부 테이블의 각 레코드마다 내부 서브쿼리를 다시 실행하고 임시 테이블을 생성할 때 표시된다.

### **Select tables optimized away**

- MIN 또는 MAX 같은 집계 함수가 인덱스만으로 처리되어 실제 테이블 접근이 필요 없을 때 표시된다.

### **Start temporary, End temporary**

- Duplicate Weed-out 최적화에서 내부 임시 테이블의 생성과 종료 지점을 나타낸다.

### **unique row not found**

- 아우터 조인에서 유니크 키로 접근했지만 일치하는 레코드가 없을 때 표시된다.

### **Using filesort**

- ORDER BY를 인덱스로 처리하지 못해 별도의 정렬 작업이 수행될 때 표시된다.

### **Using index**

- 커버링 인덱스를 사용해 데이터 파일을 읽지 않고 인덱스만으로 쿼리를 처리했음을 의미한다.

### **Using index condition**

- Index Condition Pushdown 최적화가 적용되어 스토리지 엔진 단계에서 조건 필터링이 수행됨을 의미한다.

### **Using index for group by**

- GROUP BY 처리를 인덱스를 이용해 정렬 없이 수행했음을 의미한다.
- **타이트 인덱스 스캔**
    - GROUP BY는 인덱스를 사용하지만 필요한 모든 레코드를 읽어야 하는 경우로 루스 인덱스 스캔은 아니다.
- **루스 인덱스 스캔**
    - 인덱스의 일부 키 값만 읽어 GROUP BY와 집계 처리를 수행한다.

### **Using index for skip scan**

- 복합 인덱스에서 선행 컬럼 조건이 없을 때도 인덱스를 활용할 수 있는 스킵 스캔 최적화가 적용되었음을 의미한다.

### **Using join buffer**

- 조인 시 적절한 인덱스가 없어 조인 버퍼를 사용했음을 의미한다.
- Block Nested Loop, Batched Key Access, Hash Join 형태로 표시될 수 있다.

### **Using MRR**

- Multi Range Read 최적화가 적용되어 랜덤 I/O를 줄이고 인덱스 키를 정렬해 읽었음을 의미한다.

### **Using sort_union, Using union, Using intersect**

- index_merge 접근 방식에서 여러 인덱스 결과를 합집합 교집합 정렬 병합 방식으로 처리했음을 나타낸다.

### **Using temporary**

- 중간 결과를 임시 테이블에 저장했음을 의미한다.
- 임시 테이블은 메모리 또는 디스크에 생성될 수 있다.

### **Using where**

- 스토리지 엔진에서 읽은 레코드 중 MySQL 엔진 단계에서 추가 필터링이 수행되었음을 의미한다.

### **Zero limit**

- LIMIT 0이 사용되어 실제 테이블 데이터를 읽지 않고 결과 메타 정보만 반환했음을 의미한다.

## 10장 전체 정리

- MySQL 옵티마이저는 **비용 기반 최적화**를 수행하며, 실행 계획 선택의 핵심 입력은 **통계 정보**다.
- InnoDB 통계 정보는 서버 재시작 후에도 유지되며, 필요 시 자동 또는 수동으로 갱신된다.
- MySQL 8.0부터 **히스토그램**을 통해 컬럼 단위 데이터 분포를 활용할 수 있다.
- 실행 계획은 EXPLAIN으로 확인하며, 출력 포맷보다 **컬럼 의미 이해가 핵심**이다.
- type, key, rows, filtered, Extra 컬럼이 성능 판단의 중심이다.
- type은 테이블 접근 방식을 나타내며, 위에 나올수록 일반적으로 효율적이다.
- Extra는 정렬, 임시 테이블, 인덱스 활용 여부 등 실제 실행 특성을 보여준다.
- 실행 계획은 **실제 실행 결과가 아닌 옵티마이저의 예측**이다.
- 실행 계획은 데이터 특성과 함께 해석해야 의미가 있다.
